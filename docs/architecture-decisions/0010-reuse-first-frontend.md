# ADR 0010: reuse Odoo UI behavior with platform-owned presentation

Date: 2026-10-28 (Asia/Riyadh).

Status: accepted direction; native dialog/notification/command adapters implemented and qualified. The bounded action-service seam experiment below is complete: retain native View hosting for R1. Client release fencing remains G5 work. No full WebClient replacement follows from this ADR.

## Clarification and retained work

The frontend goal is **maximum practical reuse of Odoo's existing UI infrastructure, with our own appearance and platform-specific additions**. Stock Odoo appearance is not a requirement. A custom layout does not itself justify replacing working code, and retaining Owl/assets does not by itself establish reuse of action, routing or interaction behavior.

This clarifies specification v1.1 sections 2.2, 3.2 and 16.1: adapt existing frontend functionality, use the supported root/client-action seams where practical, and keep native declarative views as the default for standard record screens. Preserve the backend, workspace authorization, independent OS approval/deployment control, current native list/form integration and framework-neutral custom-page capability. Canvas remains a supported custom page. No public SDK or authority semantics change; G2 revision7 remains the current freeze.

The current shell is a custom Owl root mounted with Odoo's `startWebClient`, not a replacement implementation of the Odoo frontend framework. Its bundle includes `web.assets_web`; `addons/web/static/src/env.js::mountComponent` starts Odoo services before mounting the root. It already imports native `View` and renders `MainComponentsContainer`. Several service reuse changes therefore do not require switching to the complete upstream WebClient.

## Smallest useful adjustment

1. Keep the current working root, visual layout, native views, workspace/plugin behavior and Canvas mounting while G5 continues. This is not approval to expand parallel generic UI behavior.
2. Before expanding generic frontend behavior, adapt confirmation dialogs, notifications and command palette/hotkeys to the already-running Odoo services. Preserve the frozen host facade. Reuse our theme/branding around native components rather than recreating their lifecycle.
3. Isolate existing native view/action/route translation from the large root component, preserving behavior. Use one bounded Notes list/form pilot to determine whether native action service/ActionContainer removes meaningful custom orchestration. Standard record screens continue to use native views; custom pages remain optional.
4. Adopt more native action/router/menu handling only where it satisfies workspace isolation, approved routes, CAS/idempotency, dirty navigation, revocation and generation disposal. Document a concrete incompatibility before adding an alternative implementation. Frontend permission display never substitutes for backend authorization.

The first adjustment is deliberately service-level reuse; extracting a helper by itself earns no product/progress credit. No frontend source/runtime changes were made during this assessment.

## When a complete WebClient change would help

The existing `addons/web/static/src/webclient/webclient.js` composes `NavBar`, `ActionContainer`, menu/action services, native routing and `MainComponentsContainer`. Extending that root could simplify standard action stacks, breadcrumbs and record navigation **if** the pilot shows those pieces can take over current orchestration without recreating it inside a client action. A component substitution alone does not demonstrate that benefit.

Such a change would replace the root's action container/navigation/history glue, and register platform screens/custom-page hosting as client actions. It would retain backend/security/deployment code, native XML views/models, public service/host contracts, workspace carrier/live authority checks, compiled plugin contributions, Canvas mount adapter, operation request screens and useful branding/theme/layout components. Adapting/replacing the NavBar template can preserve our appearance.

It would also require scoped menu generation/cache invalidation, `/app/...` deep-link translation, per-tab workspace propagation, native record revision/idempotency integration, safe dirty/session recovery and custom-page disposal across native action transitions. Source inspection alone has not established a substantial net simplification. **Do not switch the whole root now.** If the pilot establishes a clear benefit, present the concrete change/retained components and affected qualification before proceeding with that larger change.

## Implemented service reuse

`platform_addons/mp_shell/static/src/native_interactions.js` delegates confirmation to `dialog.add(ConfirmationDialog)`, notifications to `notification.add`, and command registration/search to `command.add/openPalette`. The root uses the native hotkey service, whose dispatch chooses one matching registration; the parallel window key handler and root confirmation/command dialogs are removed. Only current authorized platform commands appear. Retire native dialogs, notifications and command registrations on mount/identity/workspace changes; stale cached callbacks recheck availability. The framework-neutral facade, public namespaced plugin command execution and optional Canvas hosting remain intact.

Keep the custom header/sidebar/theme/layout and plugin dialog styling. Apply theme and direction to native overlays, including accessible selected-row colors. Native list/form views remain the standard record host. A browser fast-save test found that the custom save callback bypassed native input commit: call native `record.checkValidity` before reading DTO fields, retain the existing service/CAS/idempotency path, and show Saved after navigation. This reuses native validation rather than adding widget state handling.

## Bounded native action-service seam experiment

Completed 2026-10-28. Evidence: `docs/evidence/G5/20261028T163000Z-native-action-seam/action-seam.json`; reproduce in a NEW evidence directory with `node tools/probe_native_action_seam.mjs --output docs/evidence/G5/<fresh-run-id>`.

Hypothesis: replacing direct native View with ActionContainer and passing the existing platform callbacks through action-service `options.props` would remove list/form orchestration while retaining public routes and save behavior. Execute the actual pinned, unmodified `_getViewInfo` function in an isolated Node process, stubbing only enclosing service calls. It overwrites `selectRecord`, `createRecord` and `updateActionState`: selection42 and creation call native `switchView(form, {resId:42/false})`, and mounted state changes call native `pushState`. Neither platform public-UUID route callback runs. The custom `saveRecord` and `onDiscard` callbacks survive. ActionContainer itself only renders the action manager's current component; it supplies no workspace/public-ID translation.

Decision: keep the existing native View adapter for R1. It already reuses Odoo list/form controllers, renderers, widgets and validation. Its remaining route/public-ID/CAS/idempotency integration is required platform glue. Direct substitution through the proposed seam does not preserve route ownership; a full WebClient/client-action integration would require deeper navigation translation rather than simply removing this glue. No demonstrated substantial simplification warrants replacing the root. Keep native views as the default and optional framework-neutral Canvas mounting, with the qualified native dialog/notification/command services.

This is a discriminating source-function experiment, **not** a complete browser/clone pilot or proof that every WebClient integration is incompatible. Source inspection found a concrete seam mismatch before a live prototype was warranted; the bounded experiment resolves this R1 design choice without a candidate rebuild or site/database mutation. No new UI acceptance pass or progress increase follows. Historical references above to a future action/view pilot describe the earlier sequence; this result closes that assessment, not UI07 or full UI09.

For UI07, inspected upstream `addons/bus/static/src/services/assets_watchdog_service.js` and `addons/bus/static/src/outdated_page_watcher_service.js`. They reuse native notification/reload presentation, but only warn on bus/server-version/missed-notification signals; they do not compare the platform's published release epoch or fence stale mutations. Reuse native notification/dialog/browser facilities for controlled reload while implementing the necessary platform release comparison, mutation fencing and draft handling. Do not add bus merely to obtain an advisory refresh message. If a backend endpoint/dispatch change is required, ADR0015's static-only deploy restrictions still apply: implement explicit versioned native-core maintenance rather than relaxing them.

User clarification, 2026-10-28: Canvas remains a minimal reference/test plugin, not a separate product. UI changes are for required demonstrations, accessibility or defect correction. Keep native Odoo views for standard CRUD. Fresh-reference setup may use an explicit reproducible workspace-scoped fixture provisioning procedure; a new public create API, self-service product UI or Canvas polish is not required merely to seed this demonstration. Keep this distinct from claiming the existing one-off board already proves fresh installation.
