# ADR 0019: manager preparation through the staged native planner

Date: 2026-10-28. Status: source, actual scoped manager install, independent authority and release-refresh resume qualified. Actual first native install and adjacent manager upgrade qualified on29October; upload/details and full G5 remain in progress under G5-X02/E-01b.

Sections 8, 10.6 and 20 require manager preparation of install/upgrade plans followed by independent local approval, apply and observed results. The existing manager only prepared suspend/enable; the staged CLI already implements native install/upgrade, grants, checkpoint, maintenance, readiness and recovery. Extend the manager's existing proposal path rather than add a second executor or replace the UI root.

The local operator stages an immutable candidate with `plugin stage-image`, then publishes its sanitized preview using `tools/publish_profile.py --staged`. This explicit preview step reads the private StageStore under the existing deployment/site locks and revalidates its base configuration, actual image metadata and curated artifacts. It copies only the five-digest descriptor and inspected runtime into the untrusted planning profile. No private configuration, store paths, approval, credentials or executable instructions are published. Native installation can stage the current image; staging does not imply changing executable bytes. Ordinary profile publication during activation/recovery clears the optional preview, so stale candidates do not persist across release changes. Older application images require their original profile shape; publish the optional preview only after deploying a compatible core reader.

Browser nominations retain the frozen plugin/site/workspace/version/digest fields. They cannot select images, commands, paths, installation identities, grants or approval. The data-only manager adapter verifies the artifact against the staged image, derives stable installation IDs and scoped dependency/provider closure, lists every existing scope of changed shared native packages (including suspended scopes), and requires explicit dependent-change consent for other plugins. Existing availability is retained. Ambiguous providers, missing/suspended required dependencies, unrelated candidate changes without valid targets, omitted sites, incompatible versions and malformed/stale previews fail closed through the existing solver/planner. No plugin code is imported while preparing.

Use `prepare_staged_plan` for both native install and upgrade proposals, including current-image installs. This keeps permission expansion and exact independent reconstruction on one path. A local operator must stage a candidate before native manager preparation; the application does not build/acquire a runtime itself. Current-image CLI preparation remains supported separately. Upload acquisition/validation remains distinct from image construction, trust enrollment, plan request and execution; this item does not claim the upload screen is complete.

Store the resulting plan as the same immutable application request, with absent scopes honestly shown as not_installed/planned. Existing operator-role, own-request and release-pin checks remain. Local `operations import-request`, exact-hash `operations approve`, `plugin apply` and `operations mirror-status` inspect the same operation. The UI displays those commands and identifies local path placeholders; those paths come from the operator's configuration, never from package/browser data. Native/full-trust, permission and destructive acknowledgements remain local. Independent validation reloads the actual private stage and deployment, recomputes the full proposal, and rejects forged or changed previews before reservation/mutation. Public profile metadata confers no authority.

No frozen request/view/plan/service/host schema, public major, golden serialization or frozen file changes. The optional staged_release field is internal sanitized planning-cache data, not an approval protocol. Its reader accepts the prior exact profile shape. Source tests must verify this compatibility and the unchanged 78-file freeze. Core native code changes require mp_core19.0.0.1.2 to1.3; changed shell source accompanies mp_shell19.0.0.1.3 to1.4. Deploy through the existing exact core_upgrade operation before testing manager requests. Standard record screens remain native Odoo views, and Canvas remains a minimal reference.

Required evidence: data-only target/consent/artifact/stale-preview/independent-reconstruction tests, preserved feature/approval consumers, JS syntax/assets, then actual native core deployment and manager install/upgrade request/import/approval/apply/status walkthrough on named disposable targets. Verify workspace admins cannot request/execute native maintenance, forged app approval remains inert, all unchanged data/scopes/bindings survive, and original operation status remains visible after release refresh. Source checks alone do not close G5-X02 or SEC-06. Existing fault/recovery evidence is retained; no OS-crash qualification is inferred.

The manager also retains only an opaque operation ID and request nonce in session storage, keyed by authenticated principal and site. After a release reload it rechecks session/operator authority and fetches the same own-request status before displaying anything; polling continues without retaining the old prepared form. An uncertain submit keeps the same nonce for an explicit retry. This hint is never approval, plan content or authority. Changing actors, losing the operator role or receiving own-request denial clears the relevant hint. Browser storage can be unavailable; the independent local journal remains authoritative. Native Odoo navigation/dialog services and CRUD hosting are unchanged.
