# ADR0030: reuse bound services for native job authorization

Date: 2026-10-29. Status: F-01b1 accepted; F-01b2 pending. Builds on ADR0029 and the frozen identity/binding/worker contracts.

The durable primitive is qualified, but its typed storage scope is not authority. Reuse the existing native `call_bound` checks for job authorization and actual service invocation. Extract its authorization result as a private bound-call object; synchronous calls retain schema validation and actor-preserving behavior. Background jobs reconstruct a fresh native environment from the stored principal/workspace foreign keys, current backing-user mapping and current credential state. A serialized role, user ID, consumer label or result cannot supply authority.

F-01b is implemented in two bounded steps. F-01b1 supplies registered jobs, current authorization before computation and again before fenced finalization, safe status and an inventoried native runner. F-01b2 supplies commit-safe producer events, authorized topic delivery/consumer deduplication and the host-event transport. New public DTOs must be frozen before consumers; the first step uses private native job envelopes and the existing public document service.

Private envelopes retain the original binding, credential scope, request/trace IDs and validated input. Queue identity comes from current server metadata. Deduplication compares semantic input/binding/handler version rather than fresh correlation IDs, preserving the first request's trace without rejecting a legitimate repeat. Binding or release changes conflict. Saved outcomes still require current authorization.

Claims commit before computation. The detached invocation contains only bounded JSON and a claim, never a native environment or administrator cookie. Finalization reacquires the current job fence and metadata authorization, reconstructs the original actor environment and applies the result through the registered bound service in the same transaction as job completion. Revocation committed during computation prevents application. Native serialization/deadlock retries may repeat database transactions, not external computation. Errors expose fixed codes and identifiers, never exception values, job input or SQL.

The reference native jobs inspect a Note revision and normalize a Note title through its existing document service. Normalization is the required small idempotent database job, with expected-revision CAS and an observable native business effect. These jobs add no Canvas functionality or alternative CRUD UI. Notes receives a new immutable package version; existing service schemas and old artifacts remain valid.

Use a separate fresh disposable G6 integration site for the next versioned core/package candidate. The populated F-01a fixture remains paused and untouched: its existing G5 recovery adapter deliberately cannot recover populated queue tables. This is a distinct integration fixture, not a reset/retry or a claim of upgrade/restore qualification. The complete G6 queue-aware lifecycle/recovery path remains required in F-01e before final G6 qualification.

The native job runner validates inventoried code and database/release pins before importing Odoo, then uses ordinary mapped users for business handlers. It has the host application's database access, as a native backend component. The separately operated reference stats worker remains a different process with no Odoo import, database password, unrestricted filestore or issuer private key. No hostile-code confinement or human delegation token is introduced.

The first unpublished Notes0.2.4 candidate exposed a real compatibility gap: its old platform range admitted core1.7, which lacks the new private job API. Retain that counterexample and reject the candidate without curation or native installation. Notes0.2.5 requires platform>=0.1.8,<0.2. Observe the selected image's inventoried platform version statically and require its corresponding native core version; never infer an old deployment's capabilities from the current host tools. Images without that declaration retain platform0.1.0. An actual read-only observation of the previous G6 image reproduces its complete published lock/metadata exactly. Candidate02 is installed on its own fresh site through exact independent approval; twelve native authorization tests pass using retained source-bound results and one corrected private exception assertion.

The first actual standalone runner launch on candidate02 passed its immutable startup guards but failed before registry creation or job claim: bare `import odoo` does not initialize Odoo19's namespace package. Import the native `Registry` and `config` explicitly after the guards. Retain the stopped child and unclaimed job (attempts0/business revision1), and pause this site. Candidate03 changes only the SDK bootstrap/runtime inventory; package/core/dispatch code remains exact. Its real process/death/reclaim check uses a distinct fresh owned site, with no populated-queue upgrade bypass. This bounded fixture is necessary because the existing lifecycle adapter explicitly rejects populated queues; F-01e remains required for upgrade/restore qualification. No reset or native migration replay is performed.

[F-01b1 qualification](../evidence/G6/20261029-job-auth-01/qualification.json) passes on candidate03: twelve source-bound native authorization cases; actual guarded normal runner, SIGKILL after committed claim, expired lease reclaim with one original-user native update and obsolete original claim rejection; eleven native/PostgreSQL plus four Linux default-kernel regression tests; twelve HTTP scheduler CRUD denials and native list/form plus synchronous CRUD/CAS checks. Eight protected configurations, full G5 audit, previous G6 queues and authorization metadata remain exact. JOB-01/02 pass. JOB-03, events, the separate external worker and populated-queue recovery remain open. No frontend or Canvas change.
