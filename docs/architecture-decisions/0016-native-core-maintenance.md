# ADR 0016: explicit versioned native-core maintenance

Date: 2026-10-28. Status: exact core maintenance, pre-traffic recovery and normal rollout qualified; UI07 and remaining G5 work are in progress. This ADR does not replace exact operation approval.

UI07 needs backend release identity and stale-request enforcement in platform addons. ADR0015's `deploy` operation must continue rejecting native Python/XML/schema/version changes. A plugin upgrade cannot carry unrelated same-version core changes.

Add `core_upgrade` to the major-1 plan/public-status operation enum (freeze revision9). Existing plugin scope/artifact targets use `deploy`, meaning retain every installed native scope/package unchanged. App request DTOs continue rejecting this operator-only operation. Old consumers reject its unknown operation enum. No plugin/host/service major or old valid golden serialization changes.

Only independently staged CLI plans may select this operation. Compare exact base/candidate source and native manifests read from immutable images. Require identical curated plugin artifacts, Python solution/lock, native addon set/dependency-policy metadata and distribution policy. Allow core changes only in `mp_compat`, `mp_identity`, `mp_core`, `mp_shell` plus inventoried platform SDK/contracts. Every changed core addon must have a strictly greater canonical `19.0.X.Y.Z` native version; list exact before/after versions and all source hashes in the immutable operation lock and full local review. Reject upstream changes, unversioned native changes, addon/dependency changes, packaged plugin edits and edits/removal of already-applicable migration scripts. New applicable core migration scripts are digest bound.

Enumerate all existing installed native workspace scopes, including suspended ones; preserve stable identities, availability, grants, bindings and endpoints. No plugin migration or activation change is combined with core maintenance. Conservatively require **destructive and native-trust acknowledgements**, backup/previous-release retention and a restart even for a seemingly schema-free change: author intent cannot prove migration safety.

Use the existing deployment/site locks, independent exact reconstruction before reservation and mutation, graceful traffic/worker drain, protected coordinated checkpoint and durable mutation marker. Run native Odoo `-u` only for the exact versioned core addon list in the independently approved candidate image. Then publish the new release/inventory/epoch, select guarded replacement, verify all installed native versions, cache and readiness, and reopen traffic. Keep previous code/data/workers. Pre-traffic failures use the existing separately reviewed fresh-database restore/new epoch/resume path; never mark an uncertain migration completed or automatically restore after traffic may have opened.

Qualification: source rejection/reconstruction/ack/command tests and G2 re-freeze first; then an actual disposable versioned core upgrade, populated data/availability/binding preservation, stale-worker startup denial, controlled failure/recovery and safe-client refresh. Source-only tests do not pass UI07, G5 or native core recovery. Implementing release enforcement must separately define bootstrap pin/read semantics, both JSON gateway/native mutation fences, safe dirty draft export, explicit reload and loop prevention while reusing native UI services. Do not weaken ADR0015 or deploy an unqualified candidate.
