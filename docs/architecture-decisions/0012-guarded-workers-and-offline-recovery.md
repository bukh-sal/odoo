# ADR 0012: select guarded workers and recover without booting failed code

Date: 2026-10-28 (Asia/Riyadh).

Status: source, actual worker replacement/recovery, native lifecycle, crash/concurrency and bootstrap consistency qualification passed under E-01d/G5; remaining gate work is tracked in implementation-status.md. Extends ADR0011; no public contract change. ADR0010 still governs frontend reuse.

Replacement workers use the exact independently approved immutable image. Keep the old containers and image, disconnect drained workers from the runtime network, and give only the new worker the `app` alias. Store its full container ID in the private deployment configuration. Image identity alone cannot distinguish retained workers when two generations use the same image. Public deployment profiles omit this operational selector.

Before importing Odoo or plugins, the replacement bootstrap checks its independently passed inventory pin, every inventoried source file, exact addon search-path contents, the fixed database/configuration, database inventory pin, and installed native module versions/states. Init/update options, cron dispatch, missing pins, pending native operations and mismatches fail closed. Native maintenance remains a separate approved entrypoint. This first change guards executor-created workers; making it the default fresh-install startup path and completing BOOT-05/06 qualification remain G5 work.

Native install/upgrade metadata runs in the selected maintenance image. It preserves stable installation identities and existing feature availability, publishes scoped binding changes and exact approved capability changes, and binds the database to the target inventory. Readiness compares the full feature footprint with the checkpoint, including suspended scopes, rather than checking only that target modules are installed. Newly granted capabilities require an explicit independent permission acknowledgement, including a grant for an already packaged artifact.

Before traffic may open, a failure can leave either the base configuration or the exact approved replacement published. Recovery accepts only those configurations, using the protected checkpoint and private worker-replacement record. It binds managed worker identities and current authority in a separate expiring, exact-hash recovery review. Unknown running images require reconciliation. Observe database/native metadata offline using retained code bytes; do not require the failed application to boot or import its plugins to decide recovery.

Restore into a fresh named disposable database and selected filestore directory, retaining the failed database, old files, containers and image. Drain managed workers, recheck current human authority, overlay revocations, revoke technical credentials and rotate sessions. Verify retained code against current catalog/trust and compare restored inventory, installations and bindings with the reviewed checkpoint before native startup. Select a fresh guarded worker using the previous image, with a release generation greater than both base and failed target, so recovery never reuses an earlier epoch. Apart from the new generation/timestamp, the executable release must equal the reviewed previous release. ADR0013 preserves historical publication trust facts while independently checking current trust/quarantine; a current validation generation change does not silently relabel the restored executable lock.

Traffic stays closed until a separately reviewed resume decision. The failed operation remains retired rather than becoming completed or replaying migrations. Any post-traffic uncertainty remains outside this automatic fresh-target restore profile. Jobs/outbox, API keys or external runtimes still require the later effect/credential reconciliation profile; this ADR does not claim that profile is implemented.

2026-10-29 crash-order clarification: after acquiring deployment/database locks, inspect the durable journal before runtime preflight. If mutation may have started, the store must reconcile a lost lock owner and fence the operation before requiring a running app, revalidating the old base state or staging again. An unavailable application is expected after a maintenance crash and must not mask `recovery_required`. A later apply must never replay native work. Fresh operations retain their existing independent preflight and approval checks; completed operations return their saved result. This changes only host executor ordering, with no public contract or native runtime change. Qualification: `docs/evidence/G5/20261029-executor-crash-01/` records focused regression tests and actual process termination after a native commit, followed by explicit reconciliation and fresh-target recovery.

2026-10-29 installation-consistency clarification: an inventory pin and the versions of currently installed native modules do not prove a complete maintenance publication. Actual retained databases after native uninstall but before metadata publication still claim an installed package while its native module and field are gone. Before importing Odoo, R1 startup must also match every active native package installation to the immutable artifact identity and installed native module/version, reject native packaged modules lacking active installation metadata, and reject removed metadata with retained native registration. Never-installed packaged artifacts and inert removed history remain valid. Feature suspension retains native registration. This adds an internal read-only bootstrap check, with no public contract or schema change. `docs/evidence/G5/20261029-worker-fence-01/read-only-baseline.json` preserves the counterexample; BOOT-06 requalification and MIG-08 passed with23Windows+1Linux-onlyskip/24Linux/87freeze, five real default-entrypoint cases, exact SDK-only activation18, old17code refusal against active18DB and protected/source audit; see `docs/evidence/G5/20261029-worker-fence-01/qualification.json`. Native cron remains disabled; G6 must requalify real job/outbox workers.

Qualification must include actual Docker replacement, pre-traffic failure after target publication, fresh database/filestore restore with previous code and a newer epoch, retained old workers, business-byte preservation, and separate traffic resume. Pure source tests alone cannot pass that gate. A same-plugin-version image replacement does not qualify native schema/version upgrades, uninstall, client fencing or the complete G5 fault matrix.
