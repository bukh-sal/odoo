# ADR 0021: width-independent native numeric version comparison

Date: 2026-10-29. Status: qualified under G5-X03/VER-01 on corrected image0afd445c and exact isolated core5; G5-X04 actual database migration matrix remains open. Public contract major1/G2revision11 is unchanged.

The specification accepts canonical numeric X.Y.Z without an eight-digit component limit and maps it to19.0.X.Y.Z. A read-only pinned-source experiment proves upstream parse_version sorts0.100000000.0 before0.99999999.0: its numeric tokens are padded to only eight digits. Packaging.Version orders them correctly. The previous golden test compared packaging.Version on both sides and did not exercise the native parser. Keep the original observation; VER-01 cannot pass on the old image.

Do not narrow the package syntax or alter native version spelling to fit that implementation detail. Correct only the copied runtime parse_version.py during an R1 distribution build. Preserve the upstream checkout, copyright/license notices, alpha/final/suffix handling and tuple component/slicing behavior. Encode each numeric token by decimal-width then decimal-value, using a self-delimiting width prefix rather than a fixed pad or integer conversion. Keep the trailing-zero rules. The resulting keys remain opaque tuples of strings; both ordinary and long numeric components compare numerically. Compare the upstream legacy vectors and a broad small-component corpus against the original implementation.

The deterministic builder patch requires the exact pinned original SHA256 and exact reviewed output SHA256. Record path, patch ID, source and resulting hashes in generated_patches and the complete runtime inventory, with an entry in upstream-patches.md. The source checkout's parser stays byte-identical. A different upstream source/layout fails the build until explicitly reviewed.

The existing core-upgrade path intentionally rejects upstream changes. Add one exact exception for this reviewed source-to-output pair and exact patch attestation, requiring a strictly increasing mp_compat native version. No arbitrary upstream allowlist, manifest-provided patch authority, static deployment or plugin installation path is introduced. Unrelated files/metadata, forged attestations, missing compatibility version and reverse transitions remain denied. The exact image/source diff and native patch digest remain in the existing independently approved plan/release hashes. Recovery continues using its separately reviewed exact previous image/database/files/config rather than an ordinary downgrade.

Compatibility addon1.0 becomes1.1; public plan/approval/host/schema/golden formats and package artifacts stay unchanged. Main28 and isolated4 must remain intact until source and image checks pass, then a NEW exact core operation may update the isolated fixture. G0's historical pinned baseline evidence is retained; this is a declared R1 distribution correction, not a claim that the original baseline parser handled wide fields correctly.

Required evidence: original counterexample; invalid package spelling; ordinary/wide/very-wide numeric and native ordering; legacy equality/order and upstream vectors; exact build-preimage/output guard; positive and forged/unrelated/downgrade core-transition checks; focused resolver/CLI cases with immutable catalogs; actual corrected image parser and migration applicability; versioned native core maintenance/readiness and retained data/files/authority.
