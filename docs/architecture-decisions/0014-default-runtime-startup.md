# ADR 0014: guard the image-default R1 startup

Date: 2026-10-28 (Asia/Riyadh).

Status: implemented and qualified on a separate candidate and retained disposable database clone. Extends ADR0012/0013; no public contract change. ADR0010 still governs frontend reuse. This does not pass G5 or deploy the candidate.

The Docker default entrypoint now uses `tools/start_worker.py`. An image-owned `startup-profile` distinguishes baseline images from R1; editing inventory policy cannot downgrade the R1 profile. Baseline images retain their existing native arguments. R1 accepts only the fixed configuration path and requires independent `MP_EXPECTED_DATABASE` and `MP_EXPECTED_INVENTORY_DIGEST` values. Verify the inventory and SDK bootstrap source bytes before executing that bootstrap, then reuse its existing read-only database/native version validation before Odoo imports. Missing/wrong pins, additional CLI arguments and unsafe configuration fail closed. Maintenance remains an explicit independently controlled entrypoint, never a flag on ordinary startup.

Upstream `odoo/modules/module.py::initialize_sys_path` searches the data directory's `addons/19.0` as well as packaged addon roots. The guard therefore rejects all nonempty executable content and symlinks beneath `data_dir/addons`, allowing only empty directories Odoo creates. Require the fixed `/var/lib/modular` data directory. Check the complete inventoried `odoo`, `addons` and `packages` trees, including bytecode/cache files, and reject source symlinks. Previously ignoring `.pyc`/`__pycache__` allowed executable bytes outside the inventory. Independent image/live observation uses the same strict source policy. No upstream file is edited.

Native init/update/reinit, custom upgrade/pre-upgrade paths, language-loading and test script/tag configuration are unavailable to ordinary startup. Database inventory must match; installed/pending native module rows must match the approved source versions and have no pending operations. Native Python remains fully trusted; these checks are release integrity/operational controls, not a sandbox or protection from a Docker operator. The image ID separately binds the entrypoint/tools bytes outside the distribution inventory.

Qualification: `20261028T143000Z-default-startup-source` runs 36 host tests (one Windows symlink skip) and 36 Linux tests (including symlinks), plus the unchanged 74-file contract freeze. Candidate `60c03d32f952e477efada2f6f4e50275de5f37602d6b092d744a94e4021c6d32` is built separately under `143500Z-default-startup-candidate`. Actual default-entrypoint probes in `144000Z-default-startup` deny 25 unsafe cases without changing the clone during each attempt. A compatible default boot reaches HTTP health, preserves the complete canonical schema/data/sequence dump and passes source reinspection. The live G5 target is unchanged.

The harness first failed after all negative probes, before positive boot: its deliberate fixture updates changed COPY row order in a plain dump. Retain that failure record. Canonicalize COPY rows, retain schema/sequence/row bytes and resume the existing clone only; do not repeat database creation or completed probes. The final proof includes that reconciliation. The clone deliberately carries candidate inventory with otherwise copied/stale publication metadata and is never a published platform release. Fresh release installation and full G5 lifecycle checks remain separate.

Current executor workers still use the host-qualified explicit bootstrap to support retained older images; they already receive independent database/inventory pins. The new default is additionally protected. Historical G3/G4/G5 Compose bootstrap helpers do not establish an R1 release pin and must not be used to start a newly built R1 image by bypassing this entrypoint. Complete the supported clean-install/publication runbook at G7. Current managed G5 bootstrap commands already refuse mutation once `worker_id` exists.
