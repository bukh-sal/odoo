# ADR0046: reviewed Python dependency maintenance

Date: 2026-11-03. Status: implementation direction selected; production code, locks, contract checkpoint and deployment not changed or qualified.

G-01d2, specification §§7.4,8,10,24.4,25.3,27. The current advisory inventory includes outdated parsing, HTTP and cryptographic libraries. Package matches are review inputs, not proof of exploitability. Choosing the greatest reported fixed version is unsafe: some ranges describe Git commits, and the maintained successor to PyPDF2 has a different package name. Keep the already qualified deployment available while preparing a reviewed release.

The bounded experiment in [compatibility-summary.json](../evidence/G7/20261103-dependency-compatibility-01/compatibility-summary.json) installs seventeen exact registry candidates into a copy of the current virtual environment. Sixteen hashed binary wheels and a separately built, hashed python-ldap3.4.8 wheel satisfy the existing complete declarative dependency constraints and `pip check`. Nine native primitive checks pass against unchanged pinned Odoo/SDK source. They cover normal image processing, the existing `pypdf` adapter and encrypted PDF, HTML sanitization, HTTP handling, CBOR, actual scoped/expired RS256 token rejection, and native LDAP parsing/escaping. The initial GIF resizing expectation was wrong; pinned Odoo explicitly skips GIF resizing. Both attempts remain recorded. These results justify building a candidate, not deploying it or passing security qualification. No current candidate OSV matches is a point-in-time observation with incomplete ecosystem coverage.

Extend the existing independently staged, versioned `core_upgrade` path for deliberate Python maintenance. Do not create a second installer, install packages in live workers, treat this as a plugin upgrade, or weaken the static `deploy` restriction. ADR0016's requirement to preserve Python dependencies will be superseded only for this bounded, implemented and verified path. Its other source, native-version, checkpoint, approval and recovery restrictions remain.

The implementation must enforce:

- Independently read exact base/target image identities, full distribution metadata/content digests and Python lock digests. Preserve upstream source/patches, native addon set, curated artifact versions/digests, distribution policy and installed scopes. Require a concrete, strictly versioned core change and new SDK/platform release. Runtime interpreter/architecture compatibility must be checked explicitly; no incidental interpreter migration.
- Validate unique normalized package names and valid package versions. Refuse downgrades and unreviewed removals. Permit the explicit PyPDF2-to-pypdf replacement because pinned Odoo already contains its adapter; no new compatibility shim. Preserve all unrelated distributions. Actual changed binary/content digests are reviewable even for an unchanged version; do not claim bit-reproducible native builds.
- Resolve the complete target dependency solution using existing pure planning, target static metadata, all installed artifact constraints and exact core pins. Failure must occur before reservation/mutation. No per-package greedy installation or metadata build hooks inside the planner.
- Bind the exact target solution, lock, source/native changes and image to the existing operation hash and independent reconstruction. Ensure operator review exposes before/after dependencies, additions/removals and restart. Preserve grants, bindings, endpoint authority, plugin/native identities and availability. The application cannot request this operator-only operation.
- Use existing drain, coordinated checkpoint, native core upgrade, guarded replacement, readiness and release-epoch publication. Retain the exact old image/data for recovery. A failed candidate requires the existing reviewed fresh restore/resume; no automatic rollback after traffic opens. The separately operated worker needs its own rebuilt image, exact approval, scope and recovery qualification; changing the host image does not update it.

The existing major-1 release/operation locks already carry the complete Python solution and lock digest, and planning already explicitly updates changed target distributions. Prefer those fields rather than adding an operation type or parallel authority store. Before activation, review the semantic change under §25.3, update the contract checkpoint/compatibility fixtures and supported SDK consumers together; old validators must continue failing closed. Do not silently edit frozen artifacts. A new public field, serialization meaning or compatibility need discovered during implementation requires the appropriate schema/protocol change, not a fixture exception.

Qualification order: guard/complete-resolution/hash/independent-reconstruction negative tests and contract checkpoint; actual candidate build and native registry/HTTP/security regressions; populated reviewed maintenance plus failure/recovery preservation; separate worker rebuild/compatibility; current provenance/advisories/licenses/network/secrets; full fresh release/recovery/runbooks and affected performance/acceptance. Invalidate only affected evidence when production source/lock/environment changes; preserve the historical qualified deployment results. Remaining OS/vendor/vendored advisories are still required and may require a separately recorded substrate decision. No UI redesign or Canvas expansion follows from this change.

Dispose only of recorded owned helpers after diagnostics are archived. The experiment retired six terminal containers and created no compiler image tag. One recorded copied environment remains useful for subsequent compatibility checks; shared BuildKit cache and unrelated assets stay untouched. Retire that volume when its follow-up use ends.
