# ADR 0009: additive operator request and status API

Accepted for contract major1 revision7 before the G5 UI runtime is implemented. Existing plan/approval hashes, workspace/host/service DTOs and G0-G4 authority semantics remain compatible.

The new negative fixtures also exposed an existing validator edge: Python regex `$` accepts a position before a final newline. A plan operation UUID with a terminal newline passed the old JSON schema. Tighten anchored schema patterns with the portable `(?![\s\S])` absolute-end assertion, including property-name patterns. This is a compatible correction to the already documented canonical identifier/digest/version intent, not a newly accepted spelling. New/embedded plan examples and all existing valid fixtures remain unchanged. Current G4 runtime/image stays its previously qualified source; strengthened consumer checks are requalified statically now and on the G5/G7 runtime. No OS approval bypass was observed: independent reconstruction already canonicalizes UUID targets.

The specification already requires an application operator to prepare/request/view operations, with independent local OS approval. Add strict `operations-request` and `operations-view` schemas and examples. A current authenticated human with an explicitly operator-provisioned application operator role may use these endpoints. Workspace administrator status alone provides no such role. Technical principals cannot request host control. Operator-role provisioning remains a local operation; no HTTP role-grant endpoint is added.

Routes under `/api/v1/operations/`: GET context/catalog, POST prepare/request, GET an authorized operation's status. Use the existing bounded session/CSRF/envelope/error rules. Requests contain only plugin/site/workspace/artifact identities and a cascade declaration, or exact operation ID/hash/request ID. They accept no shell text, credentials, database names, URLs, deployment commands, authority flags or approval records. Install/upgrade nominate exact numeric version/digest; native uninstall/unregister/artifact removal are site operations. Feature enable/suspend names explicit workspaces. Restore preparation remains the independent operator recovery CLI, while its progress can be mirrored to the UI.

Preparation returns a frozen v1 plan envelope and exact proposed targets/diff. The complete operation-lock preimage is retained with the untrusted app request for independent CLI retrieval/reconstruction; its digest is already in the approved v1 plan (ADR0008). App metadata/profiles/catalog/status mirrors are untrusted proposals. The executor re-observes actual targets and current independently configured catalog/trust, reconstructs the exact plan and authenticates the OS owner before approval/apply. An application database flag or copied operation ID grants no host authority.

The UI has no privileged Approve action. It displays the local exact-hash approval/apply step and observes a redacted journal mirror. Response metadata declares its source, observation time and staleness, and keeps artifact/release/database/feature/service dimensions distinct. It must call native suspension feature suspension and never claim it unloads Python/overrides. Labels/descriptions/notes are escaped text. Status includes bounded codes/IDs, never native traces, document contents, credentials or OS allowlist records.

For portable offline validation, operations-view embeds the unchanged plan schema as a local definition, with an equality test against the original source; no remote schema retrieval is introduced. These are additive endpoints, not methods on the ordinary plugin host facade. Existing consumers require no migration. New fixtures test unknown authority keys/majors, canonical identifiers, exact artifacts, site-versus-workspace scope, declaration/status metadata and full embedded-plan validation. G2 revision7 must pass before handlers are enabled; real operator/nonoperator/CSRF/queue/status/browser qualification remains G5.
