# ADR 0018: retain and prepare native public host assets

Date: 2026-10-28. Status: qualified under UI-RELEASE-01/G5-X01; G5 remains in progress.

Section 19 requires immutable content-addressed assets and release compatibility. The actual generation21-to22 test found that Odoo's `AssetsBundle._clean_attachments` deletes older bundle metadata; `Binary.content_assets` then redirects an old checksum URL to the current bundle. The old blob alone surviving in the filestore does not keep its URL usable. See `../evidence/G5/20261028-client-refresh-static-normal-01/asset-retention-diagnosis.json`.

Extend the pinned native `ir.qweb._get_asset_bundle` factory only for the production `mp_shell.assets_host` bundle. Its `AssetsBundle` subclass retains prior attachment metadata/blobs instead of cleaning older versions. Unrelated bundles and debug generation delegate to native behavior. Native compilation, URL construction, attachment checksum computation, exact asset lookup, streaming, MIME and cache headers remain Odoo's implementation. No new cache server, browser framework, CRUD host or Canvas feature is introduced. Public cache retention does not change private/workspace attachment authorization.

The native seven-character version truncates a timestamp/path descriptor rather than hashing immutable image contents. Host versions therefore use the full SHA256 of the read-only image inventory digest, full native variant descriptor, bundle name and asset type. Native URL construction accepts the full digest. This binds addresses to release contents even when source timestamps match; regular legacy seven-character URLs remain served from retained metadata. Preflight records the actual compiled body SHA256 separately.

Keep retained versions until a separately defined operator retention decision permits retirement; no automatic purge is added. This does not retroactively reconstruct assets already deleted by older development releases. Qualify the current published URLs and future versions with exact byte checks and redirects disabled. Preserve and report historical missing paths honestly.

The independent executor also runs a fixed asset-preparation child after native state verification and before profile publication/readiness/traffic. The child validates the image inventory, raw read-only configuration DB selector before Odoo imports, and exact DB/site/deployment/release tuple, compiles the regular minified host JS/CSS, rejects missing source/invalid native XML/CSS errors/unexpected public metadata/checksum mismatches, and records hashes. Plans cannot choose source, paths, bundles or commands. This is an explicit maintenance step, not a public endpoint or a worker-start migration. Full browser/locale/RTL/accessibility testing remains necessary; this regular-bootstrap preflight is not a claim that all optional/debug/locale variants are precompiled.

Verified restores with the published-release reader run the same preparation against the restored target before a separate resume. Legacy reader0 retains its existing deferred-cache behavior. Asset preparation can write generated cache records; failures after a possible commit remain `recovery_required` with traffic closed, never a false rollback claim.

This changes native Python and the maintenance adapter, so increase `mp_shell` from19.0.0.1.2 to19.0.0.1.3 and use ADR0016's exact core_upgrade/checkpoint/acknowledgements. ADR0015 static deploy remains restricted. Public plan/service/host schemas do not change, so no new contract major or freeze revision is introduced.

Source checks: `../evidence/G5/20261028-asset-target-config-source/planning-core.json`, 65 Windows and65 Linux checks including12 new focused adapter/preflight tests, plus unchanged78-file contract freeze. Those tests use fake Odoo objects for adapter isolation; actual native checks are separately recorded below.

Revisit if the pinned factory signature changes, additional platform bundles become release-critical, or a concrete retention policy requires safe deletion of old public code assets. Do not expand this into an alternative asset pipeline without such a requirement.
