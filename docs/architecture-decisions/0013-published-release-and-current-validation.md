# ADR 0013: immutable published release, current catalog validation

Date: 2026-10-28 (Asia/Riyadh).

Status: implemented and qualified for G5-TRUST-RELEASE-01; current SDK1 adoption/rollout/restore evidence recorded below. G5 remains in progress. Extends ADR0008/0011/0012. No public v1 plan/host/service schema or golden fixture change.

The read-only reproduction125100Z shows that recomputing a current release from newly validated catalog descriptors changes its digest solely when trust policy generation changes. The image, artifact bytes, database release generation and creation time remain fixed. Historical evidence about publication must not be replaced by current policy facts.

Keep the exact published `release_lock` as optional `published_release` in the independent private deployment configuration. Reconstruct executable/environment/provider contents from actual image bytes, database bindings and currently trusted catalog as before. Require equality to the recorded lock except historical per-artifact `trust` evidence. Validate that evidence's supported shape, retain it verbatim, and require the database's published digest/generation/inventory to match. A pin does not bless changed source, Python metadata, services, manifests, frontend inventory, generation or timestamp.

Current catalog validation always precedes use of that lock. Missing, revoked or quarantined selected bytes still fail closed. Record a separate `catalog_validation_digest` in the observed internal state, covering catalog identities/versions/digests/current trust facts. Its change invalidates pending plan base-state digests. The operation lock already binds the catalog snapshot; show the current validation digest separately from historical release evidence for pinned profiles. New releases carry their own current trust evidence at explicit publication.

New worker configurations pin the exact approved target lock. A restore pins the reviewed previous executable lock with the new recovery epoch, retaining historical trust facts while revalidating present permission to run those bytes. This supersedes ADR0012's limitation that a mere current trust-generation change necessarily prevents the old lock comparison. Revocation/quarantine still prevents recovery startup; this is not a bypass or downgrade of policy.

Legacy unpinned configurations remain readable with their old projection semantics. Do not silently relabel them. An explicit local adoption under deployment/site locks accepts only an independently completed journal operation whose exact target release, immutable image, generation, timestamp and sharing sites match the actual current deployment/database. Persist the previous configuration and a proof record outside the app restore domain before atomic private configuration replacement. Adoption does not change database metadata, image, worker, release identity or traffic. Unsupported legacy baselines need their own reviewed bootstrap evidence; never guess a historical lock.

The sanitized app planning profile includes the published lock for SDK versions that implement this protocol. It remains untrusted input, never approval authority. Old images may lack the new reader; publication must detect this and preserve the existing cache rather than claim compatibility. Roll out the new reader in a separately approved image before refreshing that profile. A stale UI proposal fails independent reconstruction; it cannot authorize execution.

Qualification must prove stable release identity across current trust-generation changes, stale pending plans despite that stable identity, rejection of selected-byte quarantine/revocation/tampered pins and DB publication mismatch, matching app/OS projection, new-release/restore pin propagation, and actual non-mutating adoption of G5 generation9. No acceptance credit follows from this ADR alone.

A configured host validator also fences the exact private policy file before/after each archive verification. A temporary-policy test exposed that a previously constructed validator otherwise reused revoked decisions; new47host/47Linux tests cover the corrected path. The live policy was not altered.
