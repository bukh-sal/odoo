# ADR 0015: explicitly deploy platform-only image changes

Date: 2026-10-28 (Asia/Riyadh).

Status: implemented; source/contracts and normal exact approved platform deployments qualified under G5. G2 revision8 requalified. Complete deploy fault/recovery qualification remains part of the G5 matrix. Prerequisite for ADR0010 service-adapter rollout; no implicit approval follows from this ADR.

The first native-interaction candidate changes platform UI/SDK code and retains every plugin package/version. An ordinary plugin upgrade correctly refused it before approval or mutation because package versions must increase. Do not invent a plugin version or install an unrelated plugin to carry a platform update.

Add an explicit `deploy` operation/target/artifact action to the plan/status schemas in compatible contract inventory revision8, retaining major1 and all old valid DTOs/golden hashes. Older consumers must reject the unknown operation; the app request schema continues to exclude it. Only the independent staged CLI/executor prepares/applies this platform operation. The host page facade and plugin upgrade/version/migration contracts do not change.

For this bounded R1 profile, deploy requires a distinct pinned image, exact unchanged plugin artifacts and Python dependency metadata/lock, unchanged native addon set/dependencies/manifests except static asset declarations, and every existing installed native plugin/site/workspace scope explicitly enumerated. No plugin/schema migration, native addon Python/XML data change, upstream core file change, binding/endpoint change, new grant or activation change is accepted. Permitted executable deltas are platform SDK/contracts and static assets/manifests of non-package platform addons. Manifest metadata is read as data and compared excluding only `assets`. Unknown image/file changes fail closed. This is not general native core schema upgrade support.

The exact image/source diff is independently reconstructed at approval and immediately before mutation, shown in the review and hash bound. Require native trust acknowledgement, coordinated checkpoint, traffic drain, independently approved metadata publication, guarded replacement, verified automatic cache and readiness before traffic. Skip native Odoo maintenance entirely: only publish the new release/inventory/epoch with existing installation/grant/availability/binding bytes. Retain previous code/data/workers and the existing separately reviewed fresh-target recovery/resume path. A deployment is not an exception allowing same-version plugin byte replacement.

Qualify omitted scopes, no-op/same-image/empty changes, package/Python/native code/manifest-version changes, binding/permission changes, unapproved deployment, exact hash/reconstruction and actual approved platform rollout with existing data/scopes preserved. Source tests alone do not pass that qualification. Browser qualification and the bounded action/view pilot/client epoch work remain separate G5 tasks.

Existing install/upgrade/restore evidence is retained; normal deploy proof does not establish the whole new operation's fault matrix.
