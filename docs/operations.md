# Independent operator control: G5 implementation status

E-01c primitives and the initial native feature-control approval CLI are qualified. The application operations UI/queue, code-changing staged-release validation and actual apply/recovery remain in progress. There is **no working plugin apply command yet**. See [status](implementation-status.md); this document does not declare G5 passed.

The control store lives outside the application database and its restore domain. On this Windows workstation it is `.local/operator/control`, with an explicit owner SID/SYSTEM/Administrators DACL. Linux uses an owning UID and0700 directories/0600 records. OS identity comes from the authenticated system SID/effective UID rather than user-supplied environment names. Existing broadly accessible directories are rejected rather than silently changing their permissions. Store records reject links/junctions/hard-link aliases.

The current store has already been initialized. **Do not repeat init-store or the earlier observer bootstrap.** Its allowlist names only the existing disposable deployment/site UUIDs. Explicit noninteractive approval is enabled for that local qualification target; it still requires the exact reviewed hash and required destructive/trust/permission acknowledgments. The current qualification approval was revoked in `finally`; no apply or database mutation occurred.

Available local commands, using the locked tooling and operator environments:

```powershell
.venv/Scripts/python.exe tools/modular.py --config .local/operator/trust.json operations --store .local/operator/control register --bundle <draft-bundle.json> --deployment-config .local/operator/targets/r1.json --catalog .local/operator/catalog
.venv/Scripts/python.exe tools/modular.py --config .local/operator/trust.json operations --store .local/operator/control approve <operation-id> --plan-hash sha256:<hex> --deployment-config .local/operator/targets/r1.json --catalog .local/operator/catalog
.venv/Scripts/python.exe tools/modular.py --config .local/operator/trust.json operations --store .local/operator/control show <operation-id>
.venv/Scripts/python.exe tools/modular.py --config .local/operator/trust.json operations --store .local/operator/control revoke-approval <operation-id>
```

Interactive approval independently reconstructs and displays the exact targets/diff before requiring the exact hash again. `--noninteractive` works only under the independently configured policy; `--ack-destructive`, `--ack-trust`, and `--ack-permissions` provide explicit required acknowledgments. New native code and expanded permission/activation declarations require review even when a package claims compatibility. Repeating a live approval does not extend its lifetime silently. Default start lifetime is15minutes; expired starts, wrong hashes, stale state, changed operator generation, revoked records and reuse for another operation fail closed.

For the current CLI path, independent validation pins and hashes the real image/source, reads current PostgreSQL metadata through a read-only transaction, checks current curated trust and reconstructs the proposed plan. Only unchanged-release native feature suspension/enablement is accepted at this stage. Code-changing proposals deliberately fail until E-01d supplies independently staged release metadata; do not bypass that check. A record or `approved=true` flag in an application request/database cannot authorize the external store.

The library reserves each approval for one operation under exclusive OS locks, in deployment-then-sorted-site order. Locks are process held, have no expiry/takeover timer, and retain their files after release. Another directory with matching lock filenames is not ownership. Closed/replaced descriptors fence further work. A child-process crash actually releases its lock; a durable mutation-started journal record still prevents a new executor from retrying uncertain native work.

The append-oriented SQLite journal records preparation, approval/revocation, lock owner digest/PID, staging, maintenance/drain, checkpoint, mutation, worker/readiness/publication, resumed traffic and completion. Steps cannot be skipped or rewound. A native mutation requires a coordinated checkpoint reference and a fresh authority check; E-01d will verify real checkpoint contents before that call. The mutation-started record commits before launching any native child. If the parent dies, its child may still be running: a new lock owner records `recovery_required` before trying to compare the now-changed database with the original snapshot. No automatic rollback, migration retry or destructive restore is implied. Expiry after mutation starts does not kill it; revocation/changed authority still fences the next safe boundary.

Status is redacted and remains readable by a currently authorized OS operator after a policy-generation change. The eventual app adapter will mirror status without granting the application write access to approvals/journal/allowlist. Actual application isolation is already observed: UID10001, read-only root, only filestore/config volume mounts, no Docker CLI/socket and no readable/writable operator namespace. Trusted native plugins remain fully trusted inside the application; this separation does not claim to sandbox their application-data access.
