Interactive approval independently reconstructs and displays the exact targets/diff before requiring the exact hash again. `--noninteractive` works only under the independently configured policy; `--ack-destructive`, `--ack-trust`, and `--ack-permissions` provide explicit required acknowledgments. New native code and expanded permission/activation declarations require review even when a package claims compatibility. Repeating a live approval does not extend its lifetime silently. Default start lifetime is15minutes; expired starts, wrong hashes, stale state, changed operator generation, revoked records and reuse for another operation fail closed.

For the current CLI path, independent validation pins and hashes the real image/source, reads current PostgreSQL metadata through a read-only transaction, checks current curated trust and reconstructs the proposed plan. Unchanged-release native feature suspension/enablement can be reviewed, and current-image installation can be reviewed/applied for exact native artifacts already independently verified in that image. New executable bytes and other lifecycle operations still fail closed until their staged adapters qualify. A record or `approved=true` flag in an application request/database cannot authorize the external store.

The library reserves each approval for one operation under exclusive OS locks, in deployment-then-sorted-site order. Locks are process held, have no expiry/takeover timer, and retain their files after release. Another directory with matching lock filenames is not ownership. Closed/replaced descriptors fence further work. A child-process crash actually releases its lock; a durable mutation-started journal record still prevents a new executor from retrying uncertain native work.

The append-oriented SQLite journal records preparation, approval/revocation, lock owner digest/PID, staging, maintenance/drain, checkpoint, mutation, worker/readiness/publication, resumed traffic and completion. Steps cannot be skipped or rewound. A native mutation requires a coordinated checkpoint reference and a fresh authority check; The current-image installer captures actual DB/filestore archives plus previous image/config/lock references in the private store before that call; archive hashes/readability and a fresh-target restore have been exercised. The mutation-started record commits before launching any native child. If the parent dies, its child may still be running: a new lock owner records `recovery_required` before trying to compare the now-changed database with the original snapshot. No automatic rollback, migration retry or destructive restore is implied. Expiry after mutation starts does not kill it; revocation/changed authority still fences the next safe boundary.

Status is redacted and remains readable by a currently authorized OS operator after a policy-generation change. The pending app adapter will mirror status without granting the application write access to approvals/journal/allowlist. Actual application isolation is already observed: UID10001, read-only root, only filestore/config volume mounts, no Docker CLI/socket and no readable/writable operator namespace. Trusted native plugins remain fully trusted inside the application; this separation does not claim to sandbox their application-data access.

The executor uses the independently named single-site deployment and verifies its container image/mount/network topology. It stores native diagnostics privately, keeps the public edge stopped until internal registry/HTTP readiness and exact metadata/release-lock checks pass, and conservatively journals possible resumed traffic before opening the edge. A completed operation returns its existing status on replay. A possible commit/error leaves `recovery_required`; a new process cannot infer rollback or rerun the native child.

For the initial native-only recovery profile, `plugin recover prepare-restore <operation-id>` emits a canonical recovery decision/hash. Save/review its `decision` as JSON, then use `plugin recover restore <operation-id> --decision <file> --decision-hash sha256:<hex>` with the same independent `--store`, `--deployment-config`, and `--catalog` options. It restores into a fresh named disposable DB, retains the failed DB/filestore, checks exact checkpoint bytes/image/locks and reconciles current human authority before rotating session secrets and revoking technical credentials. Jobs/outbox/external runtimes/API keys require the later reconciliation profile and are rejected here. It keeps public traffic closed. `prepare-resume` followed by separately reviewed `resume` is required to reopen; both use the same CLI configuration/decision arguments. Noninteractive recovery additionally requires the explicit OS policy and exact hash. Do not repeat a failed restore over existing targets; inspect its protected recovery directory and journal.
