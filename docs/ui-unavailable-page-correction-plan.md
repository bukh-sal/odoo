## One shared correction

1. In the existing web error-handler registry, handle only actual RPC errors
   with known unavailability classifications:404/NotFound, MissingAction,
   MissingError and AccessError. Reuse the normal Dialog/Warning presentation
   with fixed translated title/body, no server text/record name/stack in that
   expected-state message. Do not classify arbitrary client errors,500s,
   validation/conflict, release mismatch, session expiry, network errors or
   caller lookalikes as ordinary unavailability. Preserve their existing paths.

2. Deduplicate concurrent expected failures per web environment while its one
   dialog is open; release that latch through the actual dialog onClose option.
   Do not retry the failed operation, navigate automatically, save/discard a
   draft, persist state or introduce a timer. A fresh menu read may recheck
   current scope; its normal fail-closed projection still owns visibility.
   A failed projection read is not a successful empty workspace.

3. Shell already renders a hidden-but-mounted action canvas plus an inline
   Workspace access changed alert and safe new-tab recovery. Remove its extra
   non-dismissible modal so that it cannot stack over the error dialog. Retain
   the hidden mounted component, exact current-menu checks, leave guards,
   context preference/focus and safe workspace new-tab behavior. Remove unused
   modal-only classes/imports only after checking callers.

4. Improve generic unexpected-error wording without hiding diagnostics or
   suggesting a blind retry after an uncertain save. Keep technical details an
   explicit support action. Neutralize inherited product labels in this common
   error surface; protocol exception names/source attribution stay unchanged.

5. Replace native Dialog back/expand/close and error-copy font glyphs with the
   exact existing pinned Lucide geometry. Preserve native callback/class/ARIA/
   slot and t-call header contracts, including SelectCreateDialog and inherited
   ActionDialog. The header is also called in another component's template;
   do not add an unbound Icon component dependency to its caller. Static SVG
   inside this one shared template is acceptable if tests compare its geometry
   with the canonical pinned data and retain notices. Where using Icon directly,
   verify the actual backend/frontend-lazy/minimal asset closure; never repeat
   the earlier backend-only dependency failure. No new icon registry/library.
