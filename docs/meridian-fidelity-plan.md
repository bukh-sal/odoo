# Meridian fidelity plan

16 November 2026 · Audit and implementation roadmap · Proposed, zero implementation milestones accepted

**Target.** On a common workflow, a user should recognize the same product in the reference and installed app from its shell, typography, navigation, content hierarchy and interactions. Use Meridian v0.5 as the rendering specification. Apply the user's roomier sizing, wider context pane, quieter filters and below-table pagination. Each other visible departure needs a named reason, an owner and a screenshot. The earlier [delivery acceptance](ui-delivery-acceptance.md) establishes a functioning baseline. This plan adds a different acceptance question: does the installed product actually look and feel like Meridian?

**First comparison:** the native Partners directory at desktop width. **Proof app:** implement Meridian Docs as a private, installable page-authoring app, working name **Pages**. The current Documents app owns files, versions, downloads and pinned references. Pages owns written pages, a hierarchy and an editor. Both should be useful independently. This choice exercises custom composition beyond a native directory or another task board.

## Rendering and style ownership

1. **Translate the reference style sheet by role.** Start with `app/src/index.css` and the accepted roomier overlay. Map background/card/popover/secondary/accent/foreground/muted/border/ring and semantic ink/fill/border triplets to the existing `--mp-ui-*` family. Add missing roles for app tint, selected row/rail marker, elevation, overlay and subtle dividers. Define text styles, mono/tabular numbers, spacing, radius, stroke, control/row heights, z-order and motion once. Preserve alpha/compositing and verify on real surfaces in both themes. Keep licensed fonts/icons inventoried and loaded locally with appropriate fallback.
2. **Give the tokens visible contracts.** Rail 56, context 264, bar 56, command max 460 × 36, title 26/34, ordinary data row 44, header about 36, primary action 34, metadata about 11, common radii 6/8/10/14 CSS px. Use 24 px desktop page inset at this width, 32 where the reference expands, and 16 on small screens subject to the matched capture. Carry the actual 1 px dividers, 1–2 line identities, typography weights, optical icon sizes, 24 px minimum small hit targets and 44 px coarse targets. Regular and compact density must apply across native and custom screens. Keep proven visible keyboard focus even if the concept ring is lighter.
3. **Own the DOM.** Start in `framework_addons/web/static/src/webclient/shell/{shell.xml,shell.js,shell.scss,app_commands.js}`. The scoped WebClient selects this Shell. Change its region order and focus order directly. Keep ActionContainer, action service, normal workspace navigation, portal/focus and access-change behavior. Consolidate shared context composition across Shell and `interface/app_layout.*`. Remove superseded visual rules as consumers migrate. Isolate legacy fallback, Bootstrap variable bridges and print behavior. Audit remaining core/optional legacy accents in compiled assets.
4. **Own view composition.** Use `search/control_panel`, `views/list`, `views/form`, `views/kanban`, `interface/page_header.*`, `record_sections.*`, `breadcrumb_trail.*`, `table_pagination.*` and `interface/surfaces.css`. Keep the search model, ORM, action history, typed field widgets, sort/select/inline-edit controllers and pagination behavior. Replace their visual templates when their hierarchy differs. Expose small optional slots for identity, metadata, toolbar, sections, summary and actions. Default native views must work with none supplied.
5. **Provide reusable recipes.** One shared sidebar item/group/tree, identity cell, badge, query toolbar, button/icon sizes, record header/tabs, reading card, drawer/inspector, empty/status and responsive master-detail layout. Reuse existing exports where their semantics fit. Each new pattern has a reference source, demo of real states, keyboard contract and at least a native and custom consumer where applicable. App CSS owns editorial prose, covers and business-specific arrangements. The base never imports private apps or the prototype's React/Zustand store.

## How fidelity will be judged

* **Reference order.** The running pinned concept defines anatomy and interactions. The signed-off roomier choices override the specific measurements listed above. Existing platform authority and truthful state override simulated controls. A low-contrast default, awkward wrapped filter or desktop-only overflow needs a documented better rendition.
* **Matched fixtures.** Create authorized synthetic records on a fresh review site using normal app paths. Match label lengths, row count, relationship, selected item, cover, content and scroll position. Use an installed provider where a field matters. For missing domains compare the same permitted subset. Also test sparse, empty, long-label and denied data. Keep previous human demo tabs intact.
* **Capture protocol.** Use the in-app browser, same CSS viewport, browser zoom, device scale factor, locale, theme, density, scroll offsets, loaded fonts and open state. Start with 1440×900 light/dark; also 1280×720 and 390×844, real 200% and RTL. Store actual computed dimensions, font family/size/weight, token values, source revision and exact installation beside originals. Capture only after content settles. Keep actual-size crops for type/icon strokes as well as whole screens.
* **Structural comparisons.** Overlay paired screens and inspect header, search center, rail/pane edges, content gutter, heading baseline, toolbar, row baseline and separators, action alignment, detail grid, inspector and focus order. Proposed working tolerances on fixed matched desktop regions: ±2 CSS px on boundaries/control heights, ±1 px on type size and icon box, ±4 px on section spacing. Review computed colors/opacity by role and rendered contrast. Mask dynamic text, dates and genuine domain data only. Never mask a missing region or compress the screenshots independently to make them align.
* **Scene list.** Empty shell; populated shell + palette/help/profile; native directory default, filtered, selected, multi-page and no results; record with and without integrations; editor + validation; modal/sheet/full-page create; board/list and task sheet; file browser and pinned revision; Pages home, editor, insert menu, tree, comments/history, viewer and conflict. Inspect hover, keyboard focus, loading and failure. Desktop A/B is the style gate; RTL, narrow, zoom, contrast and reduced motion are separate usability gates.
* **Review rule.** At phases 1, 3 and 5 show reference and installed originals at comparable scale plus the unresolved differences. For the final blind comparison use the same domain fixture, neutralize identifying text if necessary and ask what visual cue gives the implementation away. Any reproducible unintended cue in shell, typography, surface hierarchy or controls goes back to its owning phase. A passing suite, numeric average or screenshot of a mock cannot close that finding.
* **Release discipline.** Implement source changes in coherent slices, update affected substrate/asset records and package identities, run targeted regressions during iteration and a canonical host regression on frozen final source. Qualify the real installed desktop routes and narrow fallbacks. Keep the eight-addon image app-free and demonstrate that Pages and its dependencies leave the core through normal removal. Reuse unchanged recovery evidence only with an explicit source boundary.

**Resume point:** write the phase-1 execution plan against the then-current shell, renderer, private Partners source and accepted target frames. Deliver the first installed Partners comparison before authorizing wider visual rollout. This audit adds no implementation or release acceptance points.
