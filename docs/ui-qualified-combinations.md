## Intentional limits and author responsibilities

| Boundary | Reason and supported route |
| --- | --- |
| Native Python and same-origin frontend apps are trusted | Workspace gates, independent approval and scoped identities protect supported paths. Grants do not create a code sandbox. |
| Shared components provide presentation | Apps own current authorized reads, business models, drafts, revision checks, routes and explicit contributions. Use the [author catalogue](ui-author-patterns.md), actual component minima and native fallbacks. |
| Immutable image delivery | Suspension does not unload code. Database uninstall and source subtraction are separate reviewed operations; historical code/checkpoints remain for recovery. No live source injection. |
| Optional sections are an app-owned trusted seam | A new finance/sales app may supply real scoped services and sections. Core does not fabricate balances, global business search, chat or concept-only controls. |
| Current access checks cannot erase prior bytes | Fresh denial clears/hides protected UI; already rendered/downloaded content cannot be retroactively erased. Authority fixtures were restored exactly. |
| Expected missing/access pages have a bounded recovery | One friendly dialog, no private traceback/name leakage or automatic failed-write replay. Close and choose a current workspace page. Unexpected failures retain diagnostics. |

Declare restrictions deliberately from a concrete security, recovery or product
reason, rather than arbitrary app identity/version checks. New app combinations
need their own useful workflow and installed UI qualification. No production,
publication, stable ABI, broad compatibility, complex migration or long-term
support promise is made. Core/vendor notices, Partners' LGPL-3.0-only label and
private independent application boundaries remain unchanged.
