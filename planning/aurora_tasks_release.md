## Bounded application contract to prove before freezing

- List-bound tasks only. Preserve stored list/stage/task/member identities and
  existing owner/member/external-assignee rules unless a demonstrated defect
  requires a documented compatible correction. Internal active users only.
- Native record permissions remain authoritative. A platform workspace is not
  an implicit tenant or permission grant for these native application records.
  An assigned task does not confer list access. Prove the native background
  authority bridge explicitly; do not impersonate a workspace member, silently
  create grants or depend on the example Background plugin being installed.
- Completion follows the selected stage's `done` state. Define stage edits/deletion,
  list/task archive/deletion, unassignment and reassignment before implementation.
- One opt-in reminder per task occurrence, addressed to its current assignee,
  stored in a private native inbox with unread/read state. Initial delivery is
  in-app; email/SMS/push/provider effects are excluded. Existing jobs infrastructure
  supplies durable scheduling, fencing, attempts and shutdown/recovery behavior.
- Freeze explicit UTC scheduling, missed-window policy, long-future admission,
  actor revocation, recipient access/activity, edit invalidation, idempotency,
  cancellation and restore behavior after the probe establishes a feasible path.
  Do not equate a database notification row with external delivery.
- Package and native versions, dependency closure and source releases must be
  explicit. First prove the current populated native0.1.0 app can reach the new
  app release. Own R1 archive ABI remains supported; internal historical names
  are not an external-addon compatibility promise.

## Qualification boundaries

Use synthetic data, isolated environments and clearly owned fresh Docker targets.
Never replay retired AR operations or modify sealed kits. Test fresh installation,
populated data upgrade, actual denied operations, delayed jobs, edits/completion,
worker interruption and duplicate attempts, then a bounded publication fault and
independent restore. Maintenance must remain useful during the failed app's outage.
Record exact images, inventories, data witnesses, operation IDs and approvals.
Use the in-app browser for the native workflow and recipient inbox; custom pages
remain available but Canvas stays a minimal reference. Retire obsolete owned
containers/volumes/networks/images, retaining useful sealed artifacts and unrelated
assets. Do not introduce global Docker cleanup.

## Excluded and conditional

Full Aurora port/history import, standalone tasks, accounting, additional attachment
features, branding/theme/shell work, public marketplace/hostile sandbox, production
deployment, paid services and publication are excluded. Brokers, automatic scaling,
distributed providers and orchestration require measured application evidence and
a separately bounded decision. Future platform major upgrades apply when a real
breaking release is selected, not according to external Odoo releases.
